## Область и статус

- База проверки: `D:\Projects\EMS-Platform-Ex`, HEAD `587b6e0`; `git status --short` и `git diff --stat` не показали изменений. Имя ветки не проверялось.
- Цель: устранить дефекты существующих contracts, core persistence/facades и registry. Не объявлять каркас готовым MVP.
- Проверка статическая, с отдельным read-only проходом агента. Тесты, сборка и миграции не запускались; попытка `node --version` отклонена политикой инструмента, обход не выполнялся.
- План не утверждает новую модель прав, публичные контракты или схему БД. Шаг 1 является обязательным approval gate; зависимые изменения запрещены до решения владельца.
- Вне области: реализация HTTP/Next.js UI, реального LDAP-адаптера, gallery, production deployment, outbox без сценария, HA и эксплуатационная политика данных. Их отсутствие является незавершенностью MVP, а не подтвержденной сетевой уязвимостью.
- Не читать `References/`, секреты и эксплуатационные данные. Не устанавливать зависимости и не обращаться к внешним сервисам без отдельного разрешения.

## Порядок исправлений

### 1. Зафиксировать решения и потребителей до реализации

- Владелец ядра совместно с владельцами contracts и платформы согласует обновление спецификации/ADR. Устранить противоречия, сохранив уже утвержденные TTL и cookie baseline; не считать остальные предложения автоматически утвержденными.
- Определить доверенный контекст вызова admin/audit/logout: субъект выводится из проверенной сервером сессии, а не из employeeId, roles, subjectId фильтра или operatorId запроса. Зафиксировать точные права для каждой операции и выдачи защищенной роли.
- Разделить публичные данные сессии, credential и безопасную ссылку аудита. Утвердить механизм проверки credential и переход существующих синтетических сессий; cookie/CSRF/rotation HTTP-реализация остается отдельным этапом.
- Для resourceScope рекомендован минимальный вариант: отказ при запрошенной неподдерживаемой области; не придумывать правила будущих бизнес-модулей. Зафиксировать, как серверная операция задает обязательные moduleId/scope, чтобы отсутствие параметра не обходило проверку.
- Для bootstrap согласовать локальный операторский контекст и порт получения подтвержденной AD-личности без передачи паролей в argv. Без доступного порта bootstrap должен отказывать, а не генерировать личность.
- Согласовать постоянный признак bootstrap и единый конкурентный барьер для изменений административного состава. Рекомендация: singleton-запись состояния с транзакционной блокировкой; конкретная схема требует утверждения. Проверка состояния и изменение выполняются после получения барьера.
- Согласовать политику отказа регистрации audit-read, семантику expectedVersion (включая setModuleAvailability, где параметр сейчас не используется), публичные ошибки и correlation ID.
- Согласовать судьбу собственного SchemaMigrator относительно утвержденного направления node-pg-migrate и жизненный цикл таблицы версий; не добавлять второй мигратор молча.
- До изменения API перечислить потребителей через поиск импортов и вызовов: core и его тесты, apps/web, shell, demo-module, diagnostic-extension. Зафиксировать фактические вызовы отдельно от просто зависимости от contracts, версию API и согласованный переход без необоснованного compatibility layer.
- До добавления Zod или другого инструмента утвердить exact version, офлайн-источник и provenance. Статус Approved у tooling direction не заменяет это решение.

Критерий выхода: утвержденная матрица «операция → вызывающий → permission → scope → транзакция → ошибка», контрактный diff, схема/миграционный план и список потребителей. Неутвержденная часть остается заблокированной.

### 2. Создать проверки, воспроизводящие дефекты

- Сохранить быстрые unit-тесты, но не называть SQL-симулятор PostgreSQL-интеграцией: `facades.test.ts:227-229` не моделирует транзакции, а `:220-221` игнорирует SQL-пагинацию.
- Добавить отдельный integration-набор на разрешенной изолированной PostgreSQL 16 с синтетическими данными, отдельной migration-role и ограниченной runtime-role. При отсутствии стенда отмечать набор невыполненным, не подменять mock-проверкой.
- Воспроизвести F01-F12 до исправлений. Конкурентные тесты синхронизировать барьерами на двух соединениях, без ненадежного ожидания sleep.
- Не применять down и тесты отказов к общей или эксплуатационной БД.

### 3. Закрыть доверенные границы и аудит (F01, F04-F07, F11)

- После approval gate обновить contracts и все реальные потребители одним согласованным изменением.
- Поток: проверенный session credential → актуальные session/employee/roles из БД → permission/module/scope → операция → audit с фактическим actor.
- Каждый защищенный фасад проверяет полномочия самостоятельно. Logout проверяет владение/разрешение, а не доверяет произвольному ID цели. Защищенная роль не дает обхода бизнес-разрешений.
- Отсутствующая availability запрещает доступ; неизвестная запрошенная область не дает allowed=true.
- Удалить credentials из новых audit-записей, ответов чтения аудита и диагностик. Не читать существующий чувствительный аудит для проверки; миграцию/отзыв потенциально раскрытых сессий выполняет уполномоченный оператор по утвержденной процедуре.
- Actor брать из подтвержденного контекста. Критические изменения и аудит сохранять атомарно; logout не откатывает выполненный отзыв из-за последующего audit failure, но не обещает отзыв при отказе БД.
- Валидировать входы и результаты внешних портов. Преобразовывать ожидаемые ошибки в безопасный Result, сохраняя rollback при ошибке транзакции; не превращать исключение в fail внутри транзакции так, чтобы частичные записи закоммитились.

### 4. Исправить identity и конкурентные инварианты (F02, F03, F09)

- Bootstrap получает реальную пару directoryId/objectGUID через утвержденный порт; UPN остается изменяемым атрибутом, не ключом связывания.
- В одной транзакции под согласованным барьером проверить постоянный bootstrap-state, установить администратора, записать аудит и состояние завершения. Отказ любого шага не оставляет частичный bootstrap.
- Все операции, меняющие множество активных администраторов, используют тот же протокол; после блокировки перечитать состояние. Локальная optimistic version не заменяет защиту межстрочного инварианта.
- Сделать get-or-create личности конкурентно безопасным по уникальной AD-паре; два корректных первых входа находят одного сотрудника, не наследуют права другого GUID и не возвращают необработанный unique violation.
- Сохранить pending/blocked semantics и атомарность employee/session/login-audit.

### 5. Исправить persistence и registry (F08, F10, F12)

- Согласовать таблицу версий и down-процедуру, чтобы rollback не обращался к уже удаленной таблице; проверить apply → rollback → apply и ошибку посередине миграции. Не обещать безопасный rollback данных через откат приложения.
- Перевести аудит на стабильный составной порядок timestamp/id и соответствующий cursor-предикат. Валидировать формат cursor/limit/период, документировать совместимость курсоров.
- Выполнять полную runtime-валидацию manifest до изменения registry: обязательные поля, типы, kind, версии, permissions, UI и diagnostics. Невалидный ввод не оставляет частичной регистрации.
- Проверять diagnostic output, нормализовать exception/invalid result/timeout; таймаут не объявлять принудительной остановкой доверенного кода.

### 6. Закрепить проверки и согласованность каркаса

- Добавить локальные инструкции владельцев/границ пакетов без копий корневых правил безопасности.
- Добавить минимальные проверки запрещенных зависимостей, deep imports и циклов с отрицательными fixtures; выбор нового инструмента проходит tooling approval.
- Разобрать заглушку allowBuilds: если esbuild не используется, удалить устаревшую запись; если нужен, отдельно проверить build-script и утвердить boolean-политику. Не включать install scripts автоматически.
- Актуализировать документацию реализации: реально работающий каркас, mock/unit-набор, отдельные integration checks, отсутствующие HTTP/UI/LDAP и offline acceptance.

| AC-013, частично | На отдельной синтетической БД проходят clean apply, upgrade, failure/recovery и согласованный rollback. Полная Nginx/offline-приемка остается отдельной задачей. |

После разрешения исполнения запустить существующие `pnpm run typecheck`, `pnpm run build`, `pnpm run test` из корня с локальными утвержденными инструментами. Эти scripts сейчас используют TypeScript-сборку, а не Next.js production build. Новые integration/boundary scripts документировать и выполнять только после их добавления. Green unit tests не закрывают PostgreSQL concurrency и offline acceptance.

## Миграция, ревью и завершение

- Не изменять примененную 001 молча. Перед схемными исправлениями выяснить, применялась ли она на сохраняемой БД. Для сохраняемых данных подготовить новую версионированную миграцию и recovery; пересоздание допускается только на явно одноразовом синтетическом стенде.
- Не сопоставлять автоматически фиктивных bootstrap-сотрудников с AD по совпадению UPN. Исправление существующих назначений требует подтверждения личности оператором; при невозможности такой проверки перенос прав запрещен.
- Изменения permissions, contracts, bootstrap/session и миграций требуют независимого security/schema review и человеческого утверждения до релиза. Отдельный агентский проход этой проверки не утверждает будущие исправления.
- Handoff: база/ветка, измененные файлы, версии contracts и миграций, фактические команды/результаты, невыполненные проверки, остаточные риски и решения владельца. Новые доменные события не предполагаются.
- Исходники при этой проверке не менялись. Коммит не создается: пользователь запросил проверку и план, не коммит; план хранится вне репозитория. Для последующей реализации соблюдать действующие разрешения Git и не включать чужие изменения.

Использованные локальные навыки: senior-qa, senior-architect, monorepo-navigator, dependency-auditor, spec-driven-workflow; независимый проход дополнительно использовал senior-backend, senior-security, api-design-reviewer и migration-architect.
