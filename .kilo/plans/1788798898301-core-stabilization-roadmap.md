# EMS: стабилизация ядра и дальнейшие этапы

## Цель и исходное состояние

Закрыть дефекты статического ревью `e8bf7fd` и подготовить проверенное ядро к следующему этапу интеграции. База: `D:\Projects\EMS-Platform-Ex`, ветка `master`; при ревью рабочее дерево было чистым. Перед исполнением повторно проверить HEAD, рабочее дерево, применимые AGENTS.md и изменения после ревью. Не перезаписывать чужие изменения.

Это план реализации стабилизации, а не разрешение на эксплуатационный релиз или весь MVP. Результаты прежнего ревью не являются воспроизведением ошибок: тесты, сборка и PostgreSQL тогда не запускались.

Владелец решений: владелец проекта. Исполнитель исправляет core и его тесты; изменения общих проверок координирует с владельцем платформы. Независимый QA/security-ревьюер не должен быть единственным автором проверяемых исправлений.

## Согласованные решения

- Ближайший этап: стабилизация ядра. LDAP, Next.js, UI и офлайн-поставка входят только в последующую дорожную карту.
- Выдачу сессии и изменение назначения сериализовать блокировкой записи сотрудника в PostgreSQL, без добавления security-version в схему сессии.
- Если вход получает блокировку первым, последующий перевод отзывает созданную им сессию. Если перевод первым, вход после него читает новое назначение. Момент LDAP-проверки сам по себе не определяет порядок транзакций.
- Bootstrap существующего сотрудника отзывает все его сессии атомарно с назначением роли и аудитом.
- Чистая установка допустима только при отсутствии `ems_core` в начале защищённой транзакционной процедуры. Проверять под общей migration advisory lock, до создания схемы. Существующая, даже пустая, схема не считается чистой. Пустой набор миграций отклоняется.
- Обычный upgrade не переводит существующий bootstrap в `ready`. `completed` и `locked-legacy` не сбрасываются процедурой provisioning.
- Делегирование через `employees.manage` сейчас не менять. Тестами зафиксировать фактическое поведение без объявления его утверждённой IAM-политикой. До административного UI необходимо отдельное решение владельца о самоназначении и выдаче ролей сверх собственных разрешений.
- Разрешённого одноразового PostgreSQL-стенда пока нет. Подготовка стенда и разрешение очистки являются обязательными внешними условиями приёмки, а не причиной заменять её mock-тестами.

## Область и ограничения

Разрешённая область исполнения: `packages/core/src/**`, релевантные тесты core, `packages/core/package.json`; корневые scripts и новый небольшой инструмент проверки границ с тестовыми fixtures; существующие `docs/adr/0001..0003` и `docs/specs/ems-core-mvp.md` для фиксации согласованных решений и фактических статусов. `apps/web/src/composition.test.ts` можно расширить для регрессий композиции. Новые файлы должны непосредственно обслуживать эти задачи.

Публичные DTO, сигнатуры, grammar идентификаторов и схема БД не меняются по умолчанию. Для неизбежного изменения сначала представить отдельный контракт/ADR, анализ потребителей и получить утверждение. Исторические миграции `001` и `002` не переписывать; необходимость новой миграции является стоп-условием для согласования.

Не читать `References/`, реальные LDAP-данные, секреты и production-логи. Не устанавливать зависимости, не загружать инструменты и не подключаться к произвольной БД. Сохранить утверждённое временное исключение: локальные строгие валидаторы и SchemaMigrator. Использовать только имеющиеся зависимости и локальный инструментарий.

## Последовательность реализации

### 1. Зафиксировать baseline и критерии

- Прочитать навыки spec-driven-workflow, senior-qa, senior-security, migration-architect и monorepo-navigator по области работ.
- Проверить Git status/diff/log и текущие scripts. В режиме, допускающем компиляцию, выполнить существующие `pnpm run build`, `pnpm run typecheck`, `pnpm run test` без установок зависимостей. Отдельно учитывать, что существующий PostgreSQL placeholder может дать ложный успех.
- В существующих ADR/спецификации отразить согласованные выше изменения, отделить утверждённое от открытого. Не объявлять весь прежний proposal утверждённым автоматически.
- Составить короткое соответствие регрессий FR-020, FR-012, FR-026..029, FR-033..036, NFR-001 и AC-006/007/009/011/012/013. Зафиксировать исходные ошибки и пропущенные проверки.

### 2. Исправить выдачу и отзыв сессий

Файлы: `postgres-identity.facade.ts`, `postgres-administration.facade.ts`, `employee.repository.ts`, при необходимости `session.repository.ts`, `facades.test.ts`, PostgreSQL integration tests.

- Сохранить поток: directory port -> транзакция -> найденный/созданный сотрудник под row lock -> актуальные состояние и роли -> session с SHA-256 credential_hash -> audit -> commit.
- Для bootstrap/assign соблюдать порядок: singleton административного состава -> запись сотрудника -> роли и сессии. Login получает только блокировку сотрудника и не пытается потом захватить singleton. Не удерживать DB locks во время обращения к LDAP.
- Закрыть не только существующую запись, но и конкурентное первое создание личности: атомарный get-or-create, затем блокировка/актуальное чтение; не оставлять отдельную ветку bootstrap с небезопасным check-then-insert. Не активировать BLOCKED.
- В bootstrap существующей личности выполнить revoke-all внутри транзакции назначения и аудита.
- Удалить доверие к предварительно прочитанному состоянию при выдаче сессии. Ответ login должен соответствовать назначению, прочитанному под блокировкой.
- Добавить последовательную регрессию pending login -> bootstrap -> старый credential отклонён; rollback аудита bootstrap не должен оставлять ни повышение прав, ни отзыв сессий.
- Добавить детерминированные PostgreSQL interleaving-тесты для обоих порядков login/assign, login/bootstrap существующей и новой личности, двух bootstrap и двух снятий последних администраторов. Координировать соединения явными барьерами, не случайными задержками; ожидания тестов ограничить таймаутом.

Приёмка: сессия, созданная до завершившегося перевода в согласованном порядке, не работает после него; последующий вход получает новое назначение; отсутствуют дубли личности и deadlock в проверенных сценариях. Unit-тесты не заменяют PostgreSQL-доказательство.

### 3. Защитить provisioning и восстановление

Файлы: `persistence/migrator.ts`, `migrator.test.ts`, PostgreSQL integration tests.

- Проверять отсутствие схемы под migration lock до ensureMigrationTable и любых изменений. Повторный provisioning, существующие миграции/данные/схема и пустой список должны завершаться отказом без изменений.
- Применять полный clean-набор и переводить только созданное этой транзакцией состояние в `ready`, в одной транзакции. При ошибке установки схема и метаданные откатываются.
- Применить те же гарантии к `applyMigration(..., { cleanProvision: true })`, не оставляя альтернативного пути сброса. Проверить всех потребителей API. Если одиночная миграция не создаёт обязательное bootstrap-состояние, отказ должен быть явным и атомарным; не выдумывать автоматическое восстановление.
- Обычный upgrade сохраняет терминальные состояния; добавить тесты `completed`, `locked-legacy`, пустой существующей схемы, частичной установки и двух конкурентных provisioning.
- Исправить fault injection rollback-теста: ошибка именно на downSql после удаления метаданных, не на advisory lock. В PostgreSQL проверить откат метаданных и DDL после сбоя.

Развёртывание исправлений не требует новой DDL по плану. Не восстанавливать уже ошибочно сброшенные состояния автоматически: это отдельная операторская задача после анализа на разрешённом стенде. Откат приложения не является откатом БД; не рекомендовать возврат на заведомо дефектный provisioning.

### 4. Закрыть ошибки и runtime-валидацию фасадов

Файлы: identity/authorization/audit/session/administration facades, subject-auth и релевантные тесты.

- Обернуть все потенциально бросающие dependency calls, включая предварительные SQL-запросы и directory/operator ports, в согласованную нормализацию. При отказе БД доступ закрыт; внешнему потребителю возвращается безопасный Result, не raw exception.
- Сохранить прикладные CONFLICT/FORBIDDEN/UNAUTHENTICATED и специальную семантику AUDIT_FAILED просмотра журнала. Logout не откатывает уже записанный отзыв из-за последующего отказа аудита и не обещает отзыв при ошибке его записи.
- Валидировать envelope и поля ответа портов: null, массивы вместо объектов, неверные типы, пустые идентификаторы, displayName и границы размеров по существующей схеме. Неправильный ответ зависимости не считать ошибкой ввода пользователя.
- Для audit проверить типы action/subjectId, существующие ограничения cursor/limit и период. Использовать однозначные ISO/RFC3339 timestamps с timezone и проверкой календарной корректности; не полагаться на один Date.parse. Точное допустимое представление закрепить в существующем контрактном описании до изменения validator, учитывая имеющихся потребителей.
- Добавить негативные тесты на каждый dependency stage и на отсутствие побочных эффектов до завершения валидации. Не возвращать LDAP-детали, SQL, credential или hash в errors/audit.

### 5. Исправить registry без изменения формата идентификаторов

Файлы: `registry.ts`, `registry.test.ts`, при необходимости composition tests.

- Не позволять заменять сохранённый manifest через getModule/getAllModules: заморозить wrapper либо возвращать изолированные снимки. Учесть, что Object.freeze не делает Date внутренне неизменяемой; не выдавать изменяемую внутреннюю дату при выборе snapshot-подхода.
- Заменить неоднозначную конкатенацию diagnostic key на вложенные Map или однозначное tuple encoding. Не запрещать ранее допустимый `:` новым неутверждённым grammar.
- Добавить тесты замены manifest через оба getter, мутации входного манифеста, коллизии `a:b/c` и `a/b:c`, timeout, throw, error и невалидного результата диагностики. Ошибка диагностики не ломает уже валидную композицию.

### 6. Сделать проверки честными и автоматическими

- Разделить локальный запуск без стенда с явным `skip` и обязательный `test:pg`, который возвращает ненулевой код без opt-in и полного набора разрешённых параметров. Не использовать assert.ok(true) вместо приёмки.
- До любого соединения, миграции и teardown проверить явную migration/runtime-конфигурацию; не допускать fallback к ambient PG-переменным или localhost defaults. Для приёмки использовать отдельные migration/runtime роли. Не выводить строки подключения.
- На стенде разрешать DROP/cleanup только для явно подтверждённой одноразовой БД; проверка переменной сама по себе не заменяет разрешение оператора.
- Mock-тесты ограничить логикой и точной fault injection. Реальные rollback-тесты должны проверять employee, roles, sessions, availability, audit и migration metadata в соответствующих сценариях.
- Добавить без новых зависимостей checker матрицы package imports, undeclared dependencies, private deep imports, относительных обходов и циклов. Использовать имеющийся TypeScript API для разбора/резолвинга, не один regex. Проверять каждый запрещённый класс отрицательной fixture и разрешённые exports положительной.
- Подключить checker отдельным root script и в обязательную последовательность приёмки. Не менять public exports ядра в этом этапе. Клиентскую безопасность будущего Next.js bundle не объявлять проверенной статическим графом: утверждение server/client entry points и отрицательный browser build test являются блокером следующего этапа.
- Проверить audit filters и стабильную микросекундную пагинацию на реальном PostgreSQL, не mock, игнорирующем WHERE.

### 7. Независимая приёмка и передача

- Повторить build/typecheck/test, новый boundary script, строгий `test:pg` на разрешённом стенде и `git diff --check`. Записать точные команды, exit codes, passed/failed/skipped и параметры среды без секретов.
- Независимый reviewer проверяет блокировки, session invalidation, clean-state invariant, ошибки, runtime-валидацию, миграционный путь и адекватность отрицательных тестов.
- Дать владельцу отчёт о реализованном и отложенном; не выдавать characterisation-тест широкого делегирования за утверждение безопасности.
- Коммиты только согласно действующим разрешениям инструментов и явному разрешению на commit. Не обходить ограничения ради проектного требования автокоммита; при конфликте сообщить блокер. Не выполнять push, merge или release.

## Стенд и границы готовности

До PostgreSQL-приёмки владелец инфраструктуры должен предоставить и разрешить одноразовую PostgreSQL 16 БД с синтетическими fixtures, отдельными migration/runtime ролями и явно разрешённым удалением тестовой схемы. ОС, контейнеризацию и служебные учётные записи исполнитель не выбирает самостоятельно. Секреты передаются вне плана и вывода агента утверждённым способом.

**Gate A: код готов к стенду.** Исправления выполнены, локальные проверки успешны, регрессионные тесты добавлены, отсутствие PostgreSQL отражено как skip/blocked. Это не завершённая приёмка ядра.

**Gate B: стабилизация принята.** Реальные concurrency/rollback/upgrade/validation проверки успешны, P1 закрыты, независимое ревью не оставило блокеров, владелец подтвердил результат. Если стенда нет, остановиться на Gate A с точным handoff, не объявлять Gate B.

## Следующие этапы: пока не разрешены к реализации

1. **Уточнение интеграционных контрактов.** Утвердить делегирование ролей и самоназначение, критерий пригодного последнего администратора, lifecycle ролей/отделов, механизм активности/ротации сессии, CSRF, rate limits, LDAP timeouts, server/client exports, UI contribution contract и compatibility record стека. Фиксированный сейчас idle deadline не считать завершённым механизмом idle TTL; не обновлять его фоновыми запросами.
2. **Минимальный сквозной сценарий.** После решений: LDAP adapter с TLS/CA -> session cookie -> Next.js protected boundary -> core -> PostgreSQL -> read-only UI. Проверить bad password/outage/certificate, pending/blocked, отзыв и cache isolation.
3. **Административный MVP.** Утверждённые операции отделов/ролей/назначений, module availability, audit UI, shell, shared-controls gallery. Навигация должна учитывать доступность модуля отделу, не только permissions; UI не заменяет серверные проверки. Resource scope не включать как рабочую возможность до отдельного доменного контракта.
4. **Офлайн-приёмка.** Утверждённые источники и точные версии зависимостей, provenance/SBOM/licenses, bundle и runbooks, Nginx smoke на стенде без внешнего egress, clean install/upgrade/recovery. Статический SUBSYSTEMS_OPERATIONAL не считать реальной проверкой здоровья. Эксплуатационный релиз остаётся за пределами MVP.

Для этапов 1–4 потребуются отдельные исполнимые планы и согласования. Настоящий план не утверждает отложенные IAM, инфраструктурные или релизные решения.
