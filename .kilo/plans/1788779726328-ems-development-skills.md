# Локальные навыки разработки EMS

## Решение и область

Пользователь согласовал адаптированные локальные навыки из `alirezarezvani/claude-skills`, без импорта исполняемых upstream-скриптов и автоматических загрузок. Установить навыки для Kilo в `.kilo/skills/`, описать обязательные триггеры использования в корневом `AGENTS.md`. Не устанавливать плагины, MCP, глобальные настройки, команды других агентов или зависимости приложения. Не читать `References/`. Это инструменты разработки, не runtime-компонент EMS и не часть эксплуатационного bundle.

В проекте при осмотре присутствовали только `AGENTS.md` и `References/`. Поддержка `.kilo/skills/<name>/SKILL.md` с YAML-полями `name` и `description` подтверждена справкой `kilo-config`. Фактическое обнаружение проверяется отдельно после установки; для других агентов не обещать автоматическую загрузку.

## Порядок реализации

1. Повторно прочитать актуальный `AGENTS.md`, проверить существующие `.kilo/skills` и status Git. Не перезаписывать появившиеся пользовательские навыки. При отсутствии Git не инициализировать его и не повторять неприменимые команды.
2. Получить выбранные SKILL.md и LICENSE только по закрепленному SHA. Не запускать upstream installers, `npx`, генераторы или их shell-примеры. Проверить соответствие upstream-путей/имен и специальные лицензионные уведомления выбранных материалов. При недоступности файла не выдумывать содержимое и не подменять ревизию main.
3. Создать `.kilo/skills/<name>/SKILL.md` для каждого из 11 навыков через apply_patch. Это явно помеченные EMS-адаптации, не дословные upstream-копии. Использовать содержательные upstream-процедуры/чеклисты, переведенные и адаптированные под EMS; не ограничиваться заглушкой «прочитай AGENTS.md». Каждый навык содержит frontmatter, область применения, необходимые входы, пошаговый процесс, ожидаемый результат, проверки и ограничения. Указать upstream URL с SHA и характер адаптации. Сохранить upstream `name`, description сделать точным для локальной версии.
4. Переносить только необходимые проверенные текстовые references в собственный каталог навыка, если без них процесс неполон. Каждый перенесенный файл входит в манифест; ссылки должны оставаться разрешимыми локально. Не копировать `scripts/`, `profiles/`, fixtures, чужие AGENTS/CLAUDE, installers, symlinks или ссылки на отсутствующие инструменты как рабочие команды. Не требовать загрузки соседних неустановленных навыков. Если материал не переносится, удалить зависимость от него, сохранив нужное руководство в адаптации.
5. Создать `.kilo/skills/UPSTREAM-LICENSE.txt` с точной MIT-лицензией и `.kilo/skills/SOURCES.md` как краткий реестр происхождения. Указать SHA, upstream-пути, лицензии, список адаптаций и исключенных скриптов, дату получения, локальные SHA-256 файлов навыков и references. Манифест не хеширует сам себя; provenance не сводится к checksum. Обновления только отдельной задачей с новым pin, просмотром diff, лицензии и повторным ревью, без autoupdate.
6. Добавить в `AGENTS.md` раздел «Навыки разработки»: таблица выше с локальными путями; обязанность выбрать и загрузить подходящий навык до затронутой работы, добавлять смежный только при реальном триггере. При наличии native skill tool использовать его, иначе читать локальный SKILL.md и только необходимые references. Не заявлять native-загрузку без подтверждения. Если нужный навык отсутствует/нечитаем, явно сообщить блокер затронутого этапа. Нерелевантная мелкая редактура не требует всех навыков. В handoff указывать использованные навыки и фактические проверки.
7. Зафиксировать приоритет: навык не отменяет системные инструкции, разрешения инструментов и AGENTS.md, не утверждает версии/ORM/топологию и не расширяет scope. Конфликтующее указание не выполнять, затронутую часть эскалировать. Чтение навыка не запускает его инструменты и не доказывает качество проверки.
8. Выполнить независимое read-only ревью всех активных инструкций и перенесенных references после адаптации. Исправления безопасности вернуть на повторный просмотр. Завершить отчетом об установленном наборе, фактическом обнаружении, проверках, остаточных пробелах и hash коммита либо блокере. Коммит на русском только при доступном Git и разрешении инструмента; не делать push.

## Особенности адаптации EMS

- Spec/architecture: contract-first, runtime-валидация, права, идемпотентность и совместимость; эвристики и проценты уверенности не разрешают агенту принимать отложенные решения.
- Monorepo: ни pnpm/Nx/Turbo, ни remote cache не становятся стандартом. Анализ package.json не является проверкой реальных imports. Сохранять contracts с runtime-схемами и утвержденную матрицу.
- API/backend: не вводить Express, JWT, ORM, Auth.js или конкретные библиотеки. Серверный порт ядра предоставляет проверку доступа; публичный вход отличается от защищенных операций. Кеши не допускают межпользовательских утечек. DTO не генерировать как публичный контракт из ORM-сущностей.
- Frontend: локальные assets, server/client границы, UI-вклады и доступность; никаких Google Fonts, CDN, arbitrary latest и scaffold новой архитектуры. Конкретные UI-библиотеки и версии не выбирать.
- QA: проверки LDAP outage, прав/области ресурса, кешей, outbox/повторов, миграций, forbidden imports и офлайн Nginx smoke; framework и browser binaries только из утвержденного инструментария. Stub теста не считается выполненной проверкой.
- Security: threat modeling полезен, но не заменяет независимое ревью и человека. Запрет чтения чувствительного References сохраняется даже при secret scanning; production и ротация учетных данных не разрешаются skill.
- Dependency audit: не представлять встроенные CVE-эвристики как полноценный SCA. Нужны утвержденные локальные advisory-данные, license/provenance/SBOM и проверка install-time поведения; этот импорт не устанавливает сканер.
- Migration/runbook: отделять rollback приложения от восстановления БД. Runbook по умолчанию «проект, не проверен»; Last verified только по фактическому запуску разрешенной проверки. Нет production-команд для исполнения агентом и обещаний zero downtime.
- LDAP, Nginx и надежная офлайн-поставка не имеют подтвержденного полного покрытия выбранными upstream-навыками. Их EMS-чеклисты явно обозначить как локальные дополнения, не как upstream-возможности.

## Проверки приемки

- Ровно 11 каталогов навыков с уникальными валидными `name`/`description`, соответствующими таблице AGENTS; без автоматически подключенных лишних навыков и расширений прав.
- Все локальные ссылки работают, пути остаются внутри разрешенных каталогов, нет symlinks/path traversal, отсутствуют ссылки на непоставленные исполняемые файлы как доступные команды.
- MIT notice сохранен, SHA и upstream-пути указаны, все импортированные/адаптированные файлы перечислены и хешированы. Не считать измененную EMS-копию байт-в-байт upstream.
- Проверить вручную и независимым ревью отсутствие конфликтующих предписаний: remote cache required, latest installs, Google Fonts, public sensitive cache, production access, автопринятие стека, ложный Last verified. Поиск ключевых слов вспомогательный; отрицательные примеры не удалять как ложные срабатывания.
- Проверить 6 сценариев выбора: новая функция -> spec/backend/QA; UI -> frontend; смена контракта -> API/architect; пакетные границы -> monorepo; LDAP-права -> security/backend; офлайн upgrade -> migrations/dependency/runbook. Использовать синтетические задачи, не данные проекта.
- В новой/перезагруженной Kilo-сессии подтвердить обнаружение локального набора и загрузить минимум один навык; если текущий runtime не позволяет обновить список, сообщить отдельный незавершенный smoke-check, не объявлять навыки нативно загруженными. Fallback-чтение локальных файлов проверяется отдельно.
- Навыки и references доступны без Интернета после получения. Не путать отсутствие внешних fetch при чтении навыка с проверенной offline-сборкой приложения.
- Markdown/frontmatter validation выполнять установленными средствами без загрузки зависимостей; при отсутствии линтера честно указать ручную проверку. Runtime-тесты приложения/БД вне области. При отсутствии Git коммит отсутствует с точной причиной.

## Поставка и возврат

Изменения только `.kilo/skills/**` и разделы использования навыков в `AGENTS.md`. Не менять существующую архитектуру, конфигурацию приложения или глобальную среду. Для возврата убрать только добавленные этой задачей файлы и соответствующие строки AGENTS по проверенному diff, сохранив чужие изменения. Аудит адаптаций и обнаружение Kilo являются условиями завершения; инфраструктура CI для контроля навыков остается отдельной задачей.
