## Оставшиеся действия

1. **Сверить исходное состояние.** Повторно прочитать `AGENTS.md` и применимые инструкции. Однократно проверить Git через `git status --short`. Если Git отсутствует, не повторять заведомо неприменимые `git diff`, `git log` и `git commit`. Проверять изменения по исходному прочитанному тексту и примененным патчам; не выдавать это за Git diff. При появлении Git проверить чужие изменения и не включать их в свою задачу.

2. **Согласовать исключения безопасности (разделы 0, 1, 8).** Явно разграничить разрешение на локальный анализ классифицированных и минимизированных материалов и запрет их передачи внешним ИИ. Разрешение на задачу или отдельную операцию не отменяет запрет прямого доступа агентов в эксплуатационный контур. Изменение этих запретов требует отдельного утверждения политики владельцем и не отменяет системных ограничений инструмента. Не вводить исключение и не расширять доступ этой правкой. При конфликте останавливается затронутая часть, а не автоматически вся независимая работа.

3. **Уточнить air gap и происхождение поставки (разделы 2.6, 8.2, 8.3, 11).** Проверка bundle выполняется без доступа к Интернету; внутри контура разрешен только трафик утвержденной сетевой политики. Утверждение зависимости не разрешает онлайн-загрузки при офлайн-сборке или эксплуатации. Контрольная сумма подтверждает целостность относительно доверенного эталона, но сама по себе не подтверждает происхождение; способ доверенного импорта/подписи остается отдельным решением. Успешная офлайн-сборка не доказывает побитовую воспроизводимость: это отдельная проверка по утвержденным условиям. Логи, аудит, метрики и резервные копии остаются в разрешенном контуре с контролем доступа и утвержденным retention. Не выбирать численные сроки, алгоритмы подписей или инструменты.

4. **Закрыть процессные пробелы (разделы 0, 3.6, 5.2, 5.4, 13, 14).** Добавить, что адаптеры агентских инструментов используют единый источник правил, а их поддержку нужно проверять; сами адаптеры не создавать. Уточнить, что Server Components не гарантируют безопасную выдачу данных без серверной проверки доступа. Сохранить обязательность коммита на русском для успешной задачи с изменениями в пределах разрешений инструмента. Согласовать Definition of Done с отсутствием изменений: пустой коммит не нужен, успешная фиксация не заявляется при блокере. В шаблон отчета добавить hash коммита или причину отсутствия. При доступном Git перед коммитом проверить status, staged/unstaged diff, список файлов и доступную историю (`git log --oneline -10`, если история существует). Исправление причины отказа hook допустимо; отключение hook или обход отказа запрещены. Локальные проверки подбирать по изменению, не подменяя ими полный утвержденный релизный набор.

5. **Убрать дублирование без ослабления правил (раздел 3.4).** Объединить повторяющееся описание базового outbox-потока, сохранив одну нормативную формулировку и схему потока. Сохранить альтернативу только через ADR с эквивалентными гарантиями. Явно сохранить требования повторов, версии события, порядка там, где он необходим, карантина ошибок и контролируемого replay для выбранного надежного механизма. Брокер сам по себе не решает атомарность записи бизнес-данных и публикации события. Не выбирать транспорт или worker-топологию.

6. **Проверить конечный текст и пройти независимое ревью.** Проверять итоговый документ после всех правок, а не только прежнюю версию. Найденные замечания исправлять точечно; изменения безопасности после ревью возвращать на повторную проверку. Независимое агентское ревью не выдавать за человеческое утверждение. Если независимый ревьюер недоступен или остается конфликт политики, сообщить блокер, не заявляя полную приемку.

## Сценарии приемки

| Сценарий | Ожидаемый результат правил |
| --- | --- |
| Анонимный вход | Допустим только как объявленная публичная операция с серверной валидацией и ограничением частоты |
| Прямой защищенный вызов, минуя UI | Сервер проверяет сессию, разрешение и область ресурса через механизм ядра |
| UI-вклад модуля | Composition root связывает публичные контракты; ядро не импортирует реализацию расширения |
| Public subpath и private deep import | Первый разрешен только через объявленный export; второй запрещен |
| Сбой после commit и повтор события | Событие не теряется из-за fire-and-forget; повтор не дублирует бизнес-эффект |
| Альтернативный механизм событий | Требуется утвержденный ADR с эквивалентными гарантиями; сам брокер не заменяет атомарность |
| LDAP внутри контура и загрузка с CDN | Первый допустим по сетевой политике, вторая запрещена при офлайн-сборке и эксплуатации |
| Разрешение проанализировать дамп | Не является разрешением передать его внешнему ИИ или войти в production |
| Задача без изменений | Нет пустого коммита; причина отсутствия указана |
| Отсутствие Git, запрет записи или отказ hook | Нет обхода защиты и ложного сообщения о коммите; указан конкретный блокер |
| Исправление после независимого ревью | Измененная область повторно проверена, прежнее ревью не объявляется проверкой новой версии |

## Валидация и завершение

- Все исходные тематические разделы и утвержденные решения сохранены. Изменения ограничены оставшимися пунктами, без повторной реализации выполненных требований.
- Полностью прочитать итоговый документ, проверить Markdown-блоки, заголовки, нормативные формулировки и согласованность перечисленных сценариев. Поиск ключевых слов является вспомогательной проверкой, не доказательством корректности.
- Запустить Markdown lint только при наличии установленного и настроенного инструмента; ничего не скачивать. Иначе сообщить, что выполнена ручная структурная проверка, а lint не запускался.
- Runtime-тесты, миграции БД, изменения DTO/API, развертывание и rollout приложения вне области: меняются только инструкции. Технические guardrails этим документом не внедряются.
- Поставка изменения ограничена обновлением корневого документа после требуемого утверждения. При необходимости отменять только свои правки по проверенному патчу, не восстанавливать файл целиком поверх чужих изменений.
- В режиме реализации создать русскоязычный коммит только при наличии Git, изменений, успешных применимых проверок и разрешения инструмента. При блокере честно указать его. Не выполнять push, не инициализировать Git. В режиме планирования коммит не выполнять.

## Решения вне области

Стек Next.js/PostgreSQL/LDAP/Nginx, подключение доверенных модулей при сборке и локальные права сохраняются. Версии, ORM, оркестратор, конкретные UI-контракты, политика сессий, worker-топология, подпись поставки и retention остаются отложенными решениями. Новых архитектурных решений для выполнения этого плана не требуется; любые предложения ослабить безопасность должны быть вынесены отдельно, а не реализованы как редактура.
