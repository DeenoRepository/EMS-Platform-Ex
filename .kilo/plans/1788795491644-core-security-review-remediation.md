# Исправление core после ревью 0134ee0

## Цель и границы

База: `D:\Projects\EMS-Platform-Ex`, ветка `master`, commit `0134ee0`; при ревью дерево чистое. Перед реализацией повторно проверить HEAD/status и применимые AGENTS. Этот план заменяет незавершённые решения предыдущего плана исправлений для перечисленной области; предыдущий отчёт об успешном закрытии всех дефектов не считать доказательством.

Цель: устранить блокеры авторизации, bootstrap, сессий, конкурентности, миграций, аудита и runtime-валидации текущего каркаса. Владельцы: ядро, contracts, платформа; затронутые потребители обновляются согласованно.

Разрешённая область: `packages/contracts`, `packages/core`, фактические потребители в `apps/web`, shell/demo/diagnostic только при необходимости изменения публичного API; существующие спецификация и ADR, релевантные тесты/scripts. Изменение чужих областей сверх потребителей согласовывается отдельно. Не читать References, секреты и эксплуатационные данные. Не устанавливать зависимости, не запускать production-миграции.

Вне этапа: HTTP/Next.js UI, реальные OS/LDAP-адаптеры, cookie transport/CSRF/rotation/activity tracking, административный logout чужих сессий, бизнес-resource scope, переход tooling, полная offline/Nginx acceptance, общепроектный boundary-lint и локальные инструкции всех пакетов. Не объявлять результат готовым MVP.

## Утверждено владельцем в этой сессии

- Сохраняемые данные: безопасный upgrade, новые миграции, без пересоздания и переписывания применённой 001. Никакого автоматического переноса прав фиктивных AD-личностей по UPN.
- `assignEmployee`: `employees.manage`; добавление или снятие `role.platform.admin` дополнительно требует владения этой ролью. Нельзя снять последнего ACTIVE-администратора.
- `setModuleAvailability`: отдельное `modules.manage`; явная миграция выдаёт его защищённой роли. Не выводить это право из `platform.admin` автоматически во время выполнения.
- `audit.query`: `audit.view`, отказ выдачи данных при отказе регистрации просмотра (`AUDIT_FAILED`).
- Admin/audit: действующая сессия, существующий ACTIVE-сотрудник с отделом, актуальные permissions. Защищённая роль не обходит бизнес-права. Logout только собственной сессии; PENDING/BLOCKED разрешено завершить собственную действующую сессию.
- Bootstrap: отдельный внедряемый порт локального оператора подтверждает actor и `platform.bootstrap`; отдельный DirectoryIdentityResolver подтверждает AD-пару. Без портов отказ. Порты связывает доверенный composition root; произвольный operatorId не является полномочием. Реальные адаптеры вне этапа.
- Singleton-состояние bootstrap в PostgreSQL и общий `SELECT ... FOR UPDATE` барьер всех изменений административного состава. Старые установки закрыты для bootstrap до отдельной операторской проверки.
- Сессия: публичный sessionId отдельно от случайного 256-битного credential; БД хранит SHA-256 credential, не секрет. Старые сессии отзываются при upgrade, требуется новый LDAP-вход. Старые session-object IDs не возвращаются из аудита. TTL 8ч absolute/30мин idle сохраняется.
- `expectedVersion` обязателен в обеих административных операциях. У отсутствующей availability версия 0, после создания 1; дальнейшие записи увеличивают версию. Несовпадение — CONFLICT без изменений.
- Проверять полномочия назначения после получения общего барьера. По FR-021 уже авторизованная операция может завершиться при последующем отзыве; глобальный немедленный барьер всех запросов не требуется.
- Ограниченное tooling-исключение: временно сохранить SchemaMigrator, runtime-валидацию выполнить локальными функциями без новых зависимостей. Переход node-pg-migrate/Zod отдельно после exact-version/provenance approval. Зафиксировать владельца-утверждающего, scope и пересмотр до следующего tooling-изменения и до релиза в ADR.
- Реальные PostgreSQL-проверки обязательны для приёмки. Без разрешённого изолированного стенда не подключаться к произвольной БД, пометить приёмку заблокированной.

## Порядок реализации

### 1. Контракты и воспроизводящие тесты до исправлений

1. Прочитать `.kilo/skills/{spec-driven-workflow,senior-backend,senior-security,api-design-reviewer,migration-architect,senior-qa}/SKILL.md` по затронутым областям. Если native tool не знает навык, читать локальный файл, а не объявлять его отсутствующим.
2. Перечислить импорты и вызовы фасадов/портов; отличать вызовы от зависимости на contracts. Проверить public exports: `@ems/core` только `.`. Зафиксировать breaking facade revision отдельно от manifest contractVersion: изменение фасадов не требует механически ломать версию manifest.
3. Обновить существующие spec/ADR согласованными решениями; устранить противоречивые формулировки TTL, сохранив утверждённый baseline. Описать ошибки, транзакции, version semantics и переход потребителей без legacy API shim.
4. Контракт: login возвращает `{ session: publicContext, credential }`; authorize/admin/audit получают credential, не требуют доверенного клиентского SessionContext. Logout отзывает сессию credential, без произвольного target ID. Bootstrap не принимает доверенный actor из входного DTO. Порт локального оператора возвращает подтверждённые operatorId/permission, directory-порт возвращает directoryId/objectGuid/upn/displayName. Экспортировать порты через согласованную публичную точку, не deep import.
5. Добавить negative/regression tests для сценариев ниже до изменения поведения. Исправить название SQL-симулятора на unit tests; неизвестный SQL не должен молча возвращать пустой успех. Не пытаться представить симуляцию транзакций/locks доказательством PostgreSQL-инвариантов.

### 2. Безопасные миграции и metadata

1. Не изменять 001: в том числе уже закоммиченную down-версию считать потенциально применявшейся. Подготовить новую версионированную миграцию и восстановление.
2. Под migration-role и общим транзакционным migration-lock обновить metadata до первого SELECT checksum: старую таблицу без колонки, текущую с nullable checksum и новую чистую установку обработать явно.
3. Для исторических checksum не хешировать текущий произвольный SQL с предположением, что именно он был применён. Разрешать backfill только из проверенных закреплённых артефактов поддерживаемых версий и подтверждённой схемы; при неизвестном происхождении остановить upgrade до оператора. Несовпадение checksum — явный отказ. Проверять соответствие migration artifact и перед rollback.
4. Убрать распознавание SQL через includes. В транзакции проверить применённую версию и допустимый порядок rollback, удалить её metadata до down; при ошибке down rollback восстанавливает metadata. Полное удаление схемы допускается только для согласованного полного teardown на одноразовом стенде, не как произвольный откат промежуточной версии.
5. Добавить singleton bootstrap-state с явными состояниями ready/completed/locked-legacy. Чистый provisioning должен быть явным режимом migration-role на проверенной пустой установке; он создаёт ready. Обычный upgrade никогда не выводит ready из отсутствия администраторов, а ставит locked-legacy. runtime не создаёт/не сбрасывает singleton; отсутствующий state даёт отказ.
6. Добавить availability.version, существующим строкам 1; добавить уникальный nullable credential_hash и безопасную audit-ссылку/маркер формата сессии. В upgrade отозвать все старые сессии до допуска новых операций; новые записи сессий требуют hash. Старые строки не удалять самовольно.
7. Явно добавить modules.manage защищённой роли. Не создавать административные назначения людям и не исправлять фиктивные directory-пары автоматически.
8. Поставка в окно остановки старого приложения: backup уполномоченным оператором, проверка preconditions, migration, новый код, smoke, новый вход. Старый код не запускать параллельно с новым форматом. Rollback приложения не равен rollback данных; возврат к уязвимому старому коду не является штатным recovery.

### 3. Общая серверная проверка, сессии и ошибки

1. Генерировать credential через node:crypto randomBytes(32), канонически кодировать, hash SHA-256 хранить отдельно от публичного ID. Проверять формат/размер до SQL; lookup только по hash. Публичный sessionId не должен авторизовывать запрос.
2. Один внутренний механизм проверки субъекта принимает Queryable/транзакционный client; каждый защищённый фасад самостоятельно вызывает его. Проверить expiry/idle/revoke, employee ACTIVE/department и роли. Не доверять claims. При назначении получить singleton-lock до чтения сессии/прав/текущего назначения.
3. Применить матрицу прав выше. В employee assignment сохранить исторические old/new department/roles, число отозванных сессий и новую версию, всё атомарно с аудитом.
4. Availability: атомарный compare-and-set; version=0 означает INSERT при отсутствии, не unconditional upsert; concurrent creation имеет одного победителя, остальным CONFLICT. Вернуть новую version. Не конфигурированный модуль запрещён.
5. Core admin/audit операции имеют явно описанную глобальную core-область, не требуют вымышленного бизнес-moduleId. Обязательные moduleId/scope будущих бизнес-операций задаёт сервер, не пользователь. Любой запрошенный неподдерживаемый resourceScope отвергать; при необходимости обязательной области её отсутствие тоже отказ. Бизнес-scope evaluation вне этапа.
6. Runtime-валидировать все входы, optional-поля, версии, ID/длины, массивы/дубликаты, даты и ответы LDAP/operator/diagnostic портов до побочных эффектов. Неверный ввод даёт VALIDATION_FAILED, неверный порт — безопасную ошибку зависимости, не SQL/LDAP-details.
7. Не ловить ошибку записи внутри transaction callback с последующим fail/commit. Нужный rollback инициируется исключением, которое переводится в Result вне withTransaction. Преднамеренный LOGIN_BLOCKED аудит сохраняется отдельной корректной веткой. БД/LDAP/audit ошибки различать, не маскировать все под валидацию. CorrelationId генерируется на серверной границе и не содержит секретов.
8. Logout: после подтверждения credential фиксировать revoke; audit failure не отменяет уже успешный revoke. Ошибка БД не даёт ложного успеха. Повтор/истёкшая/отозванная сессия — согласованный UNAUTHENTICATED, никакого отзыва чужой сессии.

### 4. Bootstrap и конкурентная identity

1. Проверить локального оператора и подтвердить AD-личность до транзакционных записей; без resolver или при отказе не создавать отдел/роль. Ошибки портов нормализовать, результаты валидировать.
2. В транзакции получить singleton-lock, перечитать state, разрешать только ready. Найти личность исключительно по directoryId/objectGuid. BLOCKED-личность не реактивировать bootstrap автоматически.
3. Создание/назначение администратора, аудит с actor из порта и переход ready→completed выполняются атомарно. После любой ошибки state и данные неизменны. Completed/locked-legacy не сбрасываются при исчезновении ACTIVE-admin.
4. Все изменения административного состава используют этот же singleton-lock; удалить разные bootstrap/active_admins advisory locks. Зафиксировать единый порядок блокировок; прочитать last-admin count после барьера.
5. Общая конкурентно безопасная get-or-create AD-личности для login/bootstrap: INSERT ... ON CONFLICT (directory_id, object_guid) DO NOTHING, затем повторное чтение на READ COMMITTED. Не обновлять права/статус в conflict-ветке. Исчезновение записи/транзиентный конфликт — ограниченный повтор всей операции либо безопасный retryable CONFLICT, не необработанный unique violation.
6. UPN — изменяемый атрибут, не ключ прав. UPN rename сохраняет employeeId; другой GUID с тем же UPN не наследует роли. Login сохраняет атомарность employee/session/audit.

### 5. Audit и registry

1. Стабильный cursor: versioned opaque encoding timestamp/id; проверить структуру, канонический формат, длину, дату, limit 1..200 integer, periodStart<=periodEnd до SQL. Не терять микросекунды PostgreSQL при преобразовании через JS Date.
2. ORDER BY квалифицированными исходными timestamptz/id колонками, не alias timestamp::text; tuple predicate той же пары. Новый cursor-формат несовместим со старым, старые курсоры дают VALIDATION_FAILED, интерфейс начинает пагинацию заново.
3. Audit query авторизуется, читает страницу и регистрирует просмотр с настоящим actor до успешного ответа; audit insert failure возвращает AUDIT_FAILED без данных. Ошибка чтения БД — DEPENDENCY_UNAVAILABLE/INTERNAL_ERROR, не VALIDATION_FAILED.
4. Новые login/logout audit-записи используют безопасный ID, никогда credential/hash. Legacy session-object IDs маскировать в выходном DTO по доверенному маркеру формата; не раскрывать их в details/diagnostics. Не читать реальный старый аудит для отладки. Сам журнал не переписывать/не удалять автоматически.
5. Registry: проверять обязательные и optional поля manifests/permissions/UI/diagnostics, тип runner, kind/version, непустые строки, дубликаты и корректность diagnostic output до регистрации/возврата. Невалидный ввод не оставляет ownership-записей. Хранить защитную копию manifest, не позволять мутациям после регистрации обходить проверки. Ошибка/timeout/invalid output — безопасные коды; timeout не означает остановку доверенного кода.

## Проверки и приёмка

- Authorization: без credential, public ID вместо credential, подмена claims, PENDING/BLOCKED/no-department, expired absolute/idle/revoked, missing permission, unsupported scope, missing/disabled module — отказ. employees.manage без protected role не позволяет выдать/снять admin; modules.manage проверяется отдельно.
- Реальная concurrency двумя соединениями с барьерами без sleep: два последних admin removal; отзыв прав пока второй assignment ждёт singleton; concurrent bootstrap; bootstrap против admin-change; два login одной AD-пары; concurrent availability insert/update expectedVersion. Проверить FR-021, не требовать отмены уже авторизованной операции.
- Atomicity: отказ directory/operator не оставляет bootstrap-записей; отказ аудита откатывает login/bootstrap/assignment/availability; blocked login сохраняет отказной аудит; logout revoke остаётся после audit failure; DB failure не даёт успешного logout.
- Sessions: credential не хранится/не аудируется, public ID не работает как секрет; upgrade отзывает старые сессии, прежние публичные ID не принимаются, безопасная выдача legacy audit.
- Identity: bootstrap→login тот же employeeId; rename UPN; новый GUID не наследует права; повтор bootstrap после блокировки всех admin запрещён.
- Persistence: clean install и upgrade с metadata обеих старых форм; unknown/mismatched checksums; apply→rollback→apply только на одноразовой БД; failure посередине; комментарии/регистр downSql не влияют на bookkeeping. Составной cursor с одинаковыми timestamp, микросекундами, несколькими страницами, фильтрами и разными timezone offsets без пропусков/дубликатов.
- Registry: null/неверные типы/optional поля/дубликаты/мутация после регистрации, invalid runner/output, exception/timeout; никакого частичного изменения registry.
- Добавить явно запускаемый PostgreSQL integration script с pg и node:test, synthetic fixtures, отдельными migration/runtime ролями и явным opt-in на изолированную БД. Не использовать default connectionString из неизвестного окружения, не печатать секреты. Отсутствие стенда не заменять mock-проверкой и не выдавать silent skip за приёмку.
- Проверить реальные scripts и локальные инструменты. Последовательно `pnpm run typecheck`, `pnpm run build`, `pnpm run test` из корня; новые файлы включить в package test scripts (ныне они перечислены явно). Не запускать сборки параллельно: они пишут общие артефакты. Это TS build, не Next production/offline acceptance.
- Независимое security/schema/contract review после исправлений и человеческое утверждение до релиза обязательны. Не снижать проверки ради зелёного результата.

## Завершение и блокеры

План готов для реализации исходников с утверждёнными выше решениями. Production rollout не разрешён. Разрешённый PostgreSQL-стенд, проверенные исторические migration artifacts и операторская процедура обработки locked-legacy остаются отдельными условиями приёмки/поставки; отсутствие любого явно блокирует соответствующую часть, не ведёт к автоматическому reset/bootstrap.

Итог исполнителя: база/ветка, изменённые файлы, версии контрактов/миграций, фактические команды и результаты, невыполненные проверки, остаточные риски. Не помечать план завершённым только по зелёным unit tests. Commit/push — только согласно действующим разрешениям инструментов и явному запросу пользователя; само планирование не меняет исходники и не создаёт commit.
