# ADR-0003: Инструменты и офлайн-приемка MVP

- Статус: **Approved**
- Версия решения: 1.0.0
- Владелец решения: владелец проекта
- Утверждено: владельцем проекта (2026-09-07)
- Дата пересмотра: до инициализации workspace и release pipeline
- Связанные требования: NFR-001, NFR-006..007, AC-011..012

## Контекст

EMS развертывается в air-gapped-контуре. На этом этапе согласован набор направлений инструментов, но не точные версии и не источники артефактов. Нельзя считать успешной офлайн-поставку только потому, что сборка прошла на машине с сетью.

## Предлагаемое решение

1. Рассматривать pnpm workspaces без Nx/Turborepo как согласованное направление для монорепозитория; точную версию pnpm/Node/Next.js/TypeScript определить отдельным compatibility record.
2. Рассматривать `pg` с параметризованным SQL и `node-pg-migrate` как согласованное направление persistence/migrations. ORM не вводить без отдельного решения.
3. Рассматривать Zod для runtime validation и `ldapts` для server-only LDAP adapter. Точные версии, лицензии и offline availability подлежат проверке до установки.
4. Рассматривать Radix UI для сложного поведения, CSS Modules и нативные элементы для простых controls. Внешние шрифты и CDN запрещены; только локальные ресурсы и системные шрифты.
5. Сохранять server-only границу: Browser -> Nginx -> Next.js -> protected server facade -> PostgreSQL; LDAP доступен только через server-only adapter с LDAPS/StartTLS и проверкой CA.
6. Подготавливать зависимости в отдельной разрешенной среде и импортировать контролируемые артефакты на стенд. Этот ADR не разрешает агенту сетевые загрузки.
7. Предлагаемая конфигурация приемки: изолированный стенд с Ubuntu Server 24.04 LTS без контейнеров, где приложение, PostgreSQL и Nginx работают как системные службы, а AD находится отдельно на Windows Server. Изоляция и отсутствие внешнего egress являются обязательными свойствами; ОС, container mode и topology требуют отдельного утверждения владельца инфраструктуры. Это тестовый стенд, не эксплуатационная архитектура.
8. Перед релизом проверять lockfile, происхождение и подписи/иной утвержденный способ provenance, SBOM, лицензии, install/postinstall scripts, native binaries, отсутствие CDN/API/telemetry, bundle composition и отсутствие внешнего egress.
9. Документировать clean install, migration failure/recovery, отличие rollback приложения от восстановления БД, smoke через Nginx без Интернета и процедуру безопасного импорта зависимостей.

## Потоки и границы

```text
Browser
  -> Nginx (trusted ingress, headers/limits/timeouts)
  -> Next.js server boundary
  -> protected core/module facade
  -> PostgreSQL

LDAP/AD
  -> server-only LDAP adapter (LDAPS/StartTLS + CA validation)
  -> core identity/session
```

`X-Forwarded-*` принимаются только от доверенного Nginx. Клиентские заголовки не определяют роль, пользователя или отдел. Чувствительные ответы не являются публично кешируемыми.

## Рассмотренные альтернативы

- Nx/Turborepo: не выбираются на этом этапе; базовый вариант остается pnpm workspaces.
- ORM: не выбирается, чтобы не скрывать параметризацию SQL и владение схемами без отдельного решения.
- Контейнерная приемка: отклонена для согласованного MVP-стенда; вопрос production topology остается открытым.
- Онлайн-установка на стенде: отклонена, противоречит air-gapped ограничению.
- CDN, Google Fonts, online telemetry или install-time fetch: отклонены.

## Проверки до утверждения и до поставки

- Зафиксировать exact versions, source/provenance, hashes/signatures, licenses и SBOM внутри разрешенного контура.
- Проверить lockfile и install/postinstall behavior в отдельной подготовительной среде.
- Собрать и запустить на чистом offline-стенде с запрещенным неразрешенным egress.
- Проверить server-only зависимости и отсутствие секретов в client bundle, bundle и логах.
- Проверить миграции на чистой и реалистичной синтетической БД, failure/recovery и отсутствие обещания безопасного DB rollback при rollback приложения.
- Выполнить Nginx smoke без CDN, внешних API, внешних шрифтов и телеметрии.
- Утвердить internal DNS, время, trusted CA, сетевые правила, offline vulnerability data, служебные учетные записи и backup/recovery тестового стенда.

## Риски и открытые решения

- Точные версии, поддерживаемые ОС-пакеты, topology служб и package provenance не утверждены.
- Не утверждены механизм подписи bundle, ответственный за импорт, offline vulnerability feeds и формат release manifest.
- Шифрование/ротация ключей, retention, безопасное удаление и эксплуатационное восстановление находятся вне этого этапа.
- Hash подтверждает целостность относительно эталона, но без доверенного provenance не подтверждает происхождение.

## Требуемое утверждение

Утвердить tooling direction, точные версии и источники, процедуру provenance/import, состав bundle и стендовые параметры. До этого нельзя устанавливать зависимости, создавать lockfile или объявлять offline readiness.
