# ADR-0001: Состав, registry и композиция MVP

- Статус: **Approved**
- Версия решения: 1.0.0
- Владелец решения: владелец проекта
- Утверждено: владельцем проекта (2026-09-07)
- Дата пересмотра: до начала реализации registry
- Связанные требования: FR-032..036, FR-039..041, NFR-001, NFR-003, NFR-005

## Контекст

MVP должен подключать доверенные модули и расширения при сборке, не импортируя их реализации из ядра и не создавая динамическую загрузку. `apps/web` является composition root. Реестр должен обнаруживать конфликты и несовместимость до готовности приложения, а diagnostic extension не должен иметь возможности изменить вход или авторизацию.

## Предлагаемое решение

1. Разделить систему на `contracts`, `core`, `shell`, `shared-controls`, демо-бизнес-модуль, диагностическое расширение и `apps/web`.
2. В `contracts` хранить framework-neutral DTO, error envelopes, versioned extension interfaces, permission declarations и типизированные UI contribution metadata. React-компоненты не являются DTO.
3. Каждый модуль/extension предоставляет versioned manifest с уникальным глобальным `id`, `kind`, `contractVersion`, declared permissions, UI contributions и optional diagnostics.
4. `apps/web` импортирует реализации по публичным exports, валидирует manifests runtime-схемами и передает их в registry ядра. `core` принимает интерфейсы, но не импортирует реализации.
5. Registry выполняет deterministic validation: уникальность ID, поддерживаемые версии, обязательные поля, уникальность permission IDs, допустимые точки UI-вклада и отсутствие дублирования. Предлагается останавливать сборку при статически обнаружимом нарушении и readiness/startup при нарушении, обнаружимом только при композиции; точная стадия является блокирующим решением. Молчаливого пропуска нет.
6. Новая версия модуля поставляется только новым проверенным офлайн-релизом. Настройка доступности отделу меняет разрешение использования уже поставленного кода.
7. Diagnostic point вызывает проверку с ограниченным ожиданием и нормализует `ok/error/timeout`. Таймаут не является sandbox и не останавливает доверенный код; ошибка диагностики не блокирует приложение после успешной проверки состава.
8. Статический каталог gallery является вкладом демо-модуля и не смешивается с registry extension points.

## Предлагаемая схема манифеста

```text
ModuleManifest {
  id: string,
  kind: "business-module" | "core-extension",
  contractVersion: string,
  displayName: string,
  permissions: PermissionDeclaration[],
  uiContributions: UIContributionDeclaration[],
  diagnostics?: DiagnosticDeclaration[]
}
```

Это proposal: формат версий, допустимые идентификаторы, порядок регистрации, политика optional/required diagnostics, точная UI-схема и server/client entry points требуют утверждения и contract tests. Демо-модуль может поставлять UI-вклад только через декларативный registry contract и может зависеть от `shared-controls`; диагностическое расширение не получает произвольный React-вклад без отдельного extension point.

## Рассмотренные альтернативы

- Динамическая загрузка модулей после сборки: отклонена, противоречит доверенной модели и офлайн-поставке.
- Импорт реализаций из `core`: отклонен, создает обратную зависимость и скрыто связывает ядро с приложением.
- Молчаливый пропуск несовместимого вклада: отклонен, скрывает неполную поставку и делает readiness недостоверным.
- Process sandbox каждого модуля: не входит в это решение; доверенный in-process код не является sandbox-границей и требует отдельного архитектурного решения.

## Последствия и риски

- Потребуется явный composition root и публичные exports каждого пакета.
- Ошибка манифеста делает сборку/readiness неуспешной, что повышает обнаруживаемость ошибок, но требует понятного операторского сообщения без секретов.
- Внутрипроцессный registry не обеспечивает изоляцию от вредоносного доверенного кода.
- Контракты должны быть обратно совместимыми либо иметь явную версию и план перехода.

## Проверка приемки

- Contract tests на manifest, версии, permission IDs, UI contributions и diagnostic result.
- Negative tests на duplicate ID, unsupported version, deep import, отсутствие обязательного поля и неподдержанный extension point.
- Проверка, что `core` не импортирует реализации модулей/расширений.
- Проверка, что timeout/error диагностики не ломает startup после успешной registry validation; стадия отказа registry должна соответствовать утвержденному lifecycle.
- Offline smoke с заранее включенным и выключенным модулем без загрузки кода по сети.

## Требуемое утверждение

Утвердить или отклонить состав пакетов, формат manifest, правила версий, порядок регистрации, lifecycle, стадию отказа для каждого класса ошибки и readiness behavior. До утверждения реализация запрещена.
